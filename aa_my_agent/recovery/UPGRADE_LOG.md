# S11 错误恢复升级记录

## 记录规则

主循环、模型调用、停止条件和错误恢复的有意义实验、实现、回退或评估均
追加到本文件，并保留历史结论。

## 记录 01：接入 S11 模型错误恢复

### 问题

主模型请求仅能在上下文超限时压缩一次；429、529、临时网络错误会直接
终止当前进程，输出截断也没有先尝试提高模型输出额度。

### 原因

模型调用、错误分类和恢复状态混在主循环中，缺少统一的有限重试层和备用
模型状态。

### 修改

- 新增独立模型恢复模块；
- 将429、529、超时、连接错误和常见临时服务错误接入指数退避与随机抖动；
- 读取 `Retry-After` 秒数或 HTTP 日期并受最大等待时间约束；
- 连续529达到阈值后，让下一次真实请求动态使用备用模型，避免教学代码
  lambda 提前捕获旧模型的问题；
- 将输出截断改为“额度升级后重试，仍截断再无工具有限续写”；第一次截断
  草稿不进入历史，后续截断只保存文本，不保存可能不完整的工具调用；
- 保留小 A 现有上下文压缩作为 `context_length` 的恢复动作；
- 不可恢复错误和重试耗尽会返回 `failed` 结果，不再让 CLI 因模型异常退出；
- 工具执行保持在恢复层之外，禁止模型重试重复工具副作用；
- 新增 `.env.example` 配置项和结构化恢复日志。

### 验证方法

运行恢复模块单元测试、主循环测试、小 A 全量测试以及根目录回归。

### 实际结果

- S11 恢复层与主循环定向测试 19 项全部通过；
- 模拟429后模型请求成功恢复，工具处理函数只执行1次；
- 模拟连续3次529后，第4次真实请求使用备用模型；
- 模拟上下文超限时只执行1次紧急压缩并恢复；
- 第一次 `max_tokens` 会从默认额度升级到配置额度且丢弃截断草稿；再次
  截断后使用无工具续写并合并最终文本；
- 小 A 全量回归为65项通过、3项既有失败。既有失败仍是
  `test_time_tool.py` 假配置缺少 `RAG_ALLOW_ON_DEMAND_IMAGE_VERIFY`，与本次
  修改无关；
- 根目录 RAG/参考回归81项及24个子测试全部通过，仅保留既有
  `langchain-community` 弃用警告。

### 当前状态

已接入正式主 Agent 模型调用路径；不是隔离实验。默认重试5次，退避从
0.5秒开始并封顶32秒，输出额度默认从8000升级到16000，均可通过环境变量
调整。

### 剩余工作

- 当前验证使用模拟 API 错误，尚未故意触发真实服务的429/529；
- `FALLBACK_MODEL_ID` 需要用户配置与主模型 API 兼容的模型名称；
- 本次正式接入主 Agent；Subagent、记忆选择/提取和压缩摘要等辅助模型调用
  仍使用各自的降级路径，后续根据真实故障数据决定是否共用同一恢复层；
- 工具自身错误、权限、幂等和跨进程任务恢复不属于 S11 模型请求恢复范围。

## 记录 02：将 S11 整理为独立 recovery 子系统

### 问题

首版 S11 使用根目录单文件 `recovery.py`，主循环升级日志也位于
`aa_my_agent` 根目录。继续扩展 Subagent 或辅助模型恢复时，会让根目录
职责混杂，升级历史也没有紧邻对应子系统。

### 原因

第一版优先完成机制和验证，尚未建立独立 package 边界。

### 修改

- 将核心实现移动到 `recovery/model_retry.py`；
- 新增 `recovery/__init__.py`，重新导出原有公共 API，因此 `agent.py` 和
  现有测试的导入方式无需改变；
- 将主循环升级日志移动并改名为 `recovery/UPGRADE_LOG.md`；
- 删除根目录旧 `recovery.py` 和 `AGENT_UPGRADE_LOG.md`。

### 验证方法

运行：

```powershell
python -m pytest aa_my_agent/test/test_recovery.py aa_my_agent/test/test_agent_loop.py -q
```

并检查新目录文件存在、两个旧根目录文件不存在。

### 实际结果

19项 S11 恢复层和主循环测试全部通过；`recovery/__init__.py` 的兼容导入
生效，旧根目录文件均已移除。

### 当前状态

已进入正式代码结构，仅进行文件组织和导出调整，没有改变恢复行为、默认
配置或主循环逻辑。

### 剩余工作

Subagent 与辅助模型调用是否共用 recovery 子系统，仍按记录01所述等待真实
故障数据后决定；本次不扩大 S11 功能范围。

## 记录 03：压缩故障隔离与工具循环安全阀（2026-10-01）

### 问题

压缩发生在主模型异常处理之外，磁盘或压缩代码异常可退出 CLI；主 Agent 在
模型持续返回 `tool_use` 时没有每回合安全上限，可能重复运行并持续消耗额度。

### 原因

S11 只包围主模型请求，未给调用前压缩设置独立失败边界；正常开放式工具循环
也缺少只针对异常失控场景的最终保险。

### 修改

- 捕获压缩管线异常，返回可见的 `failed` 结果并保持进程可继续使用；
- 新增 `AGENT_MAX_TOOL_ROUNDS`，默认 60。正常回合仍由模型自行结束；达到
  上限时不执行该轮工具，给每个 `tool_use` 配对拒绝结果，再进行一次禁用工具
  的最终总结；若模型仍不结束，则安全停止本轮；
- 在模型请求前记录完整请求字符量，并纳入上下文预算预检。

### 验证方法

模拟压缩抛出 `OSError`；把工具轮次上限降到 2，连续返回两轮工具调用并统计
实际 handler 次数；验证最后一次模型请求的工具列表为空。

### 实际结果

压缩异常不再冒出 `agent_loop`；第二轮工具请求被配对拒绝且未执行，模型随后
完成最终说明。相关主循环、压缩、S11 和权限专项回归 48 项通过，小 A 全量
回归 129 项全部通过。

### 当前状态

已进入正式主 Agent。60 轮是异常保险，不是正常任务的目标轮数，也没有改变
开放式循环的常规结束条件。

### 剩余工作

应通过真实运行日志观察是否存在接近 60 轮的合法任务；只有取得证据后才调整
默认值。安全阀不会自动回滚上限前已经获得用户批准的外部副作用。
